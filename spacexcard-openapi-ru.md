# Открытый API ZovoCard

Программный выпуск карт, запрос данных по картам, пополнение, возврат средств, заморозка и чтение
транзакций. Каждый вызов оплачивается с баланса вашего аккаунта по вашим тарифам — так же, как в
веб-консоли.

- **Base URL (продакшн)**: `https://zovocard.com/openapi/v1`
- **Base URL (песочница)**: `https://sandbox.zovocard.com/openapi/v1`
- **Формат**: запрос и ответ — `application/json`, UTF-8
- **Учётные данные**: создайте `app_id` / `app_secret` на странице **Разработчик** после входа

> **Номера разделов совпадают с китайской редакцией** (`spacexcard-openapi`), поэтому документы можно
> сверять между собой. Китайская редакция — источник истины и обновляется первой.

### Сначала протестируйте в песочнице

Новым интеграторам следует войти на `https://sandbox.zovocard.com`, создать **отдельный ключ только
для песочницы** на странице «Разработчик» и провести интеграцию против Base URL песочницы. Аккаунты,
ключи и данные песочницы полностью изолированы от продакшна; выпуск карт, пополнения, возвраты и
транзакции имитируются — реальный эмитент не вызывается и реальные средства не двигаются.

```bash
export ZOVOCARD_API_BASE='https://sandbox.zovocard.com/openapi/v1'
export ZOVOCARD_API_KEY='sk_ваш_ключ_песочницы'

curl "$ZOVOCARD_API_BASE/products" -H "X-API-Key: $ZOVOCARD_API_KEY"
curl "$ZOVOCARD_API_BASE/balance"  -H "X-API-Key: $ZOVOCARD_API_KEY"
```

После проверки переключитесь на продакшн Base URL и **отдельно созданный** продакшн-ключ. Никогда не
используйте продакшн-ключ в песочнице и не считайте карты и транзакции песочницы реальными активами.

## 0. Ограничения аккаунта и карт

- **Минимальный ончейн-депозит — `50 USDT/USDC` за перевод.** Общий TRC20-интент ниже `50U` создать
  нельзя; перевод ниже `50U` на выделенный адрес **не** зачисляется автоматически и уходит в
  ручную обработку.
- **Резерв риска `20U` удерживается на уровне аккаунта** для стандартных аккаунтов — не по каждой
  карте и не по каждой транзакции. Он по-прежнему входит в `balance` и не создаёт отдельной проводки.
  `GET /balance` возвращает `balance`, `spendable_balance` и `account_reserve_amount`;
  **расходы, инициированные пользователем (выпуск карты, пополнение, пакетный выпуск, переводы,
  магазин, прямое пополнение), могут списываться только из `spendable_balance`.**
- **Субаккаунты не держат отдельные `20U`.** Мастер-аккаунт и все его субаккаунты используют общий
  резерв мастера, общий процент отказов, процент возвратов, суточные счётчики отказов и право на
  список разрешённых. Риск-сборы субаккаунта сначала списываются с его баланса, недостающая часть —
  с мастера; обе части фиксируются отдельными проводками. Значения `account_reserve_amount` /
  `spendable_balance` субаккаунта отражают его собственный баланс и **не** означают удержание
  дополнительного резерва.
- Сборы за отказ, за реверсал авторизации, за возврат покупки, за микропокупку и за обработку
  ограниченного мерчанта — это **платформенные риск-сборы**, они могут закрываться из резерва.
  **Не определяйте возможность операции по общему `balance`.**
- **Политика отказов**: для аккаунтов вне списка разрешённых первые 3 реальных отказа бесплатны; с 4-го
  базовый сбор `$0.30` плюс надбавка по уровню `$0.30 / $0.50 / $0.80`. Реверсалы авторизации для всех
  аккаунтов — фиксированно `1%` от суммы, они не учитываются в текущей модели риска отказов/возвратов.
  Возвраты покупок ниже `1U` бесплатны; от `1U` действует процентное правило и минимум `$0.50`.
  Верификационные возвраты Google-мерчанта ниже `1U` не учитываются в количестве возвратов, в
  знаменателе процента возвратов и в самом проценте, но полная проводка сохраняется.
  Реальные микропокупки (`0 < amount < 0.50U`) — `$0.30` за каждую.
- В данных продукта и карты возвращается `restricted_merchants` (массив заблокированных мерчантов) и
  legacy-флаг `google_chatgpt_blocked`. Если правило по BIN не настроено, карты, выпущенные не в
  Гонконге, по умолчанию блокируют `GOOGLE CHATGPT`, а гонконгские не блокируют ничего. В управлении
  продуктами можно настроить несколько мерчантов на каждый 6-значный BIN; явный пустой массив означает
  «разрешить всё». При реальной авторизации/клиринге, попадающей под любое правило: **первое**
  срабатывание замораживает карту, **второе** удаляет её, возвращает баланс карты и списывает `$0.50` —
  идемпотентно по `auth_id + rule`.
- Вывод, затрагивающий последние `20U`, считается **выходом из резерва**: нужно удалить все карты и
  выдержать `30`-дневный период наблюдения. Админский эндпоинт выплат также откажет до 30-го дня —
  не полагайтесь только на состояние кнопки во фронтенде.

## 1. Порядок интеграции

1. Создайте ключ на странице «Разработчик». Вы получите `app_id` (начинается с `ak_`, публичный
   идентификатор) и `app_secret` (начинается с `sk_`, используется для аутентификации — храните в секрете).
2. При необходимости задайте список разрешённых IP и URL вебхука для ключа.
3. `GET /products` — список доступных продуктов → `POST /cards/open` — выпуск
   (рекомендуется передавать ключ идемпотентности).
4. `GET /cards/{id}` — номер карты / срок / CVV, `GET /cards/{id}/transactions` — расходы, либо
   настройте вебхук для получения событий по картам в реальном времени.
5. `GET /balance` — баланс, `GET /balance-logs` — сверка.

> Недостаточный баланс приводит к отказу в выпуске/пополнении. Сначала внесите USDT в веб-консоли
> (поддерживаются TRON / Ethereum / BNB Chain / X Layer).

## 2. Аутентификация

Передавайте `app_secret` (начинается с `sk_`) в каждом запросе, любым из двух способов:

```
X-API-Key: sk_xxxxxxxxxxxxxxxx
```
или
```
Authorization: Bearer sk_xxxxxxxxxxxxxxxx
```

Дополнительно можно передать `X-App-Id: ak_xxxx` для двойной проверки.

- **Подписи запросов нет.** Если вы встретите где-то пример с `X-Timestamp` / `X-Nonce` / `X-Sign` —
  он устарел: эти заголовки не проверяются, и такой запрос завершится ошибкой.
- Ключи можно **включать / отключать** и задавать им **список разрешённых IP** на странице «Разработчик».
- Ошибка аутентификации — `401`; IP вне списка разрешённых — `403`.
- **Лимит: 100 запросов в минуту на ключ** по умолчанию; при превышении — `429`.
- **★Новому ключу обязательно нужно настроить список разрешённых IP, иначе он не работает★** — и это
  должен быть **исходящий IP вашего сервера**, а не IP браузера и не приватный адрес вида `192.168.x.x`.

## 3. Запросы, ответы и ошибки

Общий конверт (обратите внимание: поле называется **`msg`**, а не `message`):

```jsonc
// успех
{ "code": 0, "msg": "ok", "data": <результат> }
// ошибка (у большинства ошибок есть error_code)
{ "code": 400, "error_code": "insufficient_balance", "msg": "余额不足" }
```

> **`msg` всегда на упрощённом китайском**, независимо от языковой редакции этого документа. В примерах
> ниже сохранён китайский оригинал с переводом на русский в комментарии.
> **★Никогда не строите логику на тексте `msg`★** — см. ниже.

**★HTTP-коды значимы — не считайте, что все ответы приходят с 200★.**
Поле `code` в теле обычно совпадает с HTTP-статусом.

| HTTP | Значение | Что делать |
|---|---|---|
| 200 | Успех (`code:0`) | Читать `data` |
| **202** | **Принято, результат не определён** (возврат, удаление) | ★Ни успех, ни ошибка★ — см. «Асинхронное принятие» |
| 400 | Неверный аргумент / бизнес-ошибка | Смотреть `error_code`; обычно терминально, не повторять слепо |
| 401 | Ключ отсутствует / недействителен / отключён | Проверить `X-API-Key` |
| 403 | IP не в списке / функция не включена / нет депозита / субаккаунт без права | Различать по `error_code`, см. Приложение A |
| 404 | Объект не найден (заказ, CDK-заказ) | Проверить, что id принадлежит этому ключу |
| 409 | Конфликт (ключ идемпотентности ещё выполняется; заказ уже оплачивается и не отменяется) | Подождать и перечитать состояние, не отправлять повторно |
| 429 | Превышен лимит (по умолчанию 100/мин на ключ) | Экспоненциальная задержка |
| 500 | Ошибка сервера | Можно повторить; для записи — **с тем же `Idempotency-Key`** |
| 503 | Канал временно недоступен (сбой апстрима, размыкатель открыт) | Повторить позже или сменить `issuer` |

### ★Ветвитесь по `error_code`, а не по тексту `msg`★

`msg` — это человекочитаемый китайский текст, и он **будет меняться**. `error_code` — стабильное
машиночитаемое значение. Полный список: [Приложение A: коды ошибок](#приложение-a-коды-ошибок).

### ★Асинхронное принятие (HTTP 202): принято ≠ выполнено★

**Возврат** и **удаление** могут вернуть HTTP `202` — это значит, что апстрим принял запрос, но
результат ещё не подтверждён:

```jsonc
{ "code": 0, "msg": "退款已提交，正在确认结果", "data": { "pending": true } }
// «Возврат отправлен, результат подтверждается»
```

- `data.pending == true` → результат не определён. **Не отправляйте повторно.** Опрашивайте список
  карт / данные карты.
- `data.pending == false` (HTTP 200) → подтверждено и завершено.
- Платформа сверяет автоматически; повторная отправка может привести к дублирующей операции.

**Создание заказа на прямое пополнение работает так же**: `POST /gpt-direct/orders` возвращает HTTP
`202` с `"msg":"accepted"`. Это значит, что заказ **поставлен в очередь**, а **не** что подписка
активирована. Нужно опрашивать заказ до терминального статуса.

> ★Пополнение карты — исключение★: при неподтверждённом результате возвращается **HTTP 400** с
> текстом вида «результат пополнения подтверждается», а не 202. Повторно отправлять так же нельзя —
> дождитесь сверки.

### Два ответа, нарушающих правила (legacy, обрабатывайте особо)

| Эндпоинт | Аномалия |
|---|---|
| `GET /cards/{id}/openai-payments` | Если карты нет, возвращается **HTTP 200**, а в теле `{"code":404,...}` |
| `GET /balance-logs` | Неверные параметры фильтра дают 400 **без** `error_code` — только `msg` |

### Канал временно недоступен (различается программно)

При сбое эмитента платформа проверяет его доступность и **открывает размыкатель** для этого канала.
Выпуск карт / пополнение тогда возвращают **HTTP `503`** со стабильным `error_code`:

```jsonc
{ "code": 503, "error_code": "channel_unavailable", "msg": "渠道暂时不可用，请稍后再试或选择其他渠道" }
```

- Определяйте по `error_code == "channel_unavailable"` (никогда по тексту `msg`), затем **повторите
  позже** либо **используйте продукт другого канала** (другой `issuer`).
- Канал открывается автоматически, вмешательство не требуется. Затронут только этот канал.
- Это временный сбой, **не** ошибка списания — размыкатель отклоняет запрос до любого списания.

## 4. Идемпотентность

Для операций записи (выпуск, пополнение, возврат) передавайте уникальный заголовок `Idempotency-Key`:

```
Idempotency-Key: ваш-уникальный-id-заказа
```

В рамках одного ключа запросы с одинаковым `Idempotency-Key` выполняются **один раз**. Повтор
**возвращает первый ответ дословно** (с `Idempotent-Replayed: true` в заголовках), что и защищает от
**двойного выпуска / двойного списания** при сетевых повторах.

- Формат: `A-Za-z0-9._:-`, 1–80 символов. Неверный формат — `400`.
- Кэшируются только **2xx**. Ошибки не кэшируются, поэтому тот же ключ можно повторить.
- Если запрос с тем же ключом ещё выполняется, сервер ждёт до **30 секунд**, затем возвращает `409`.

## 6. Описание эндпоинтов

Все пути указаны относительно Base URL. Все эндпоинты требуют аутентификации (§2).
Операции записи дополнительно требуют зачисленного депозита на аккаунте, а для субаккаунтов — наличия
соответствующего права.

### 6.1 Список доступных продуктов

`GET /products`

Без параметров. Возвращает продукты, доступные **вам**, с **вашими** тарифами.

Основные поля: `product_code`, `issuer`, `bin`, `network`, `issuing_area`, `card_type`, `open_fee`,
`base_open_fee`, `recharge_fee`, `min_amount`, `max_amount`, `refund_keep_min` (может быть null),
`enabled`, `exclusive`, `min_vip_level`, `restricted_merchants`, `google_chatgpt_blocked`, а также
опциональные `usage_policy` / `bin_heads` / `bin_notes`.

Передавайте `product_code` в эндпоинты выпуска карты ровно в том виде, в каком он возвращён здесь.

### 6.2 Выпуск карты

`POST /cards/open` — право субаккаунта: `open_card`

| Поле | Тип | Обяз. | Правила |
| --- | --- | --- | --- |
| `product_code` | string | да | ≤32 символов |
| `first_name` | string | да | ≤64 символов |
| `last_name` | string | да | ≤64 символов |
| `init_amount` | number | да | `≥ 1`; также ограничено min/max продукта |
| `remark` | string | нет | ≤1200 символов |
| `max_on_daily`, `max_on_monthly`, `max_on_percent`, `transaction_limit`, `transaction_limit_type` | — | нет | **Только канал 4**; в остальных игнорируются |

Возвращает объект карты. **Передавайте `Idempotency-Key`.**

> ★Лимит расходов API-ключа★: предпроверка использует `init_amount`, но фактически на ключ
> записывается `init_amount + open_fee`. Учитывайте это при выборе лимита.

> **Синхронно или асинхронно**: каналы 1 и 3 часто работают асинхронно. Таймаут возвращает сообщение
> «результат подтверждается» — **карта всё ещё может быть выпущена**. Проверьте список карт, а не
> повторяйте запрос.

### 6.3 Пакетный выпуск

`POST /cards/batch-open` — право субаккаунта: `open_card`

Тело как в 6.2 плюс `count` (целое, **1–50**).

```jsonc
{ "code": 0, "msg": "ok", "data": {
  "success": [ /* объекты карт */ ],
  "failed":  [ { "index": 2, "error": "余额不足" } ]   // «Недостаточно средств»
} }
```

- Ошибки предпроверки (баланс, продукт, политика) отклоняют **весь** запрос с 400/403/409/503.
- Ошибки по отдельным картам попадают в `data.failed[]`, а HTTP-статус остаётся **200**.
- Карты выпускаются последовательно; ошибка на поздней карте **не** откатывает уже выпущенные.

### 6.4 Мои карты

`GET /cards`

| Параметр | По умолч. | Примечание |
| --- | --- | --- |
| `page` | 1 | Значения `<1` приводятся к 1 |
| `page_size` | 20 | Максимум **100** |
| `q` | — | Поиск по номеру карты или примечанию |
| `issuer` | — | `one` / `three` / `four` |
| `status` | — | `ACTIVE` / `FROZEN` / `DELETED` |
| `balance_sort` | — | `asc` / `desc` |
| `archived` | все | Только `""`, `"0"` или `"1"`; иначе **400** |
| `sync` | — | `"1"` синхронизирует баланс с апстримом для текущей страницы |
| `exclude_ids` | — | Id карт через запятую, до 500 |

Возвращает `{ "total": N, "list": [ /* карты */ ] }`.

> Карты канала 2 никогда не появляются в списках.
> `status=DELETED` показывает только завершённые удаления; карта в процессе удаления остаётся в
> активном списке с заполненным `delete_pending_at`.

### 6.5 Данные карты (номер / срок / CVV)

`GET /cards/{id}`

Объединяет данные апстрима с локальными полями: `card_number`, `cvv`, `expire`, `status`,
`available_amount`, `card_type`, `card_address`, `limit`, плюс локальные `id`, `remark`, `issuer`,
`product_code`, `refund_keep_min`, `min_recharge`, `restricted_merchants`, `channel_payable`, `bin_note`.

- Для `issuer=four` дополнительно возвращаются `balance_as_of` (Unix-секунды) и `balance_stale`,
  а имя и адрес держателя намеренно пустые.
- `status` всегда **локальное** значение.
- Если запрос к апстриму не удался, но карта есть локально, вернётся **200** с частичными данными.

> ★Этот эндпоинт возвращает полный номер карты и CVV. Считайте это чувствительными данными и
> маскируйте их в логах.★

### 6.6 Транзакции по карте

`GET /cards/{id}/transactions` — `page` (1), `page_size` (20, макс. 100), `sync=1` для предварительной
сверки. Возвращает **плоский массив** (без `total`).

### 6.7 Референсные цены OpenAI для BIN-сегмента

`GET /cards/{id}/openai-payments`

Всегда возвращает **3 уровня** (`plus` / `x5` / `x20`) с `label`, `min_usd`, `max_usd`, `amount`,
`time`, `found`. Уровни без данных имеют `found:false`.

> Это **референсные цены по BIN-сегменту**, а не обязательно списания по конкретно этой карте.
> Если карта не найдена, возвращается HTTP **200** с `code:404` в теле (см. §3).

### 6.9 Пополнение карты

### 6.10 Возврат с карты (баланс карты обратно на баланс платформы)

|---|---|---|
| Сразу | 200 | `{"code":0,"msg":"退款成功，余额已退回","data":{"pending":false}}` |
| Асинхронно | **202** | `{"code":0,"msg":"退款已提交，正在确认结果","data":{"pending":true}}` |

### 6.11 Лимиты расходов по карте (канал 4 / StarLink)

### 6.18 API прямого пополнения (GPT / Claude / Grok)

> **Параметр тарифа 50x: `"plan": "pro_50x"`, продукт `"product": "gpt"`.** Это значение используется для прямого пополнения и выпуска CDK. Поле запроса — `plan`, а не `plan_type`.

Прямое пополнение использует карту в вашем аккаунте для активации или апгрейда подписки на ИИ-сервис.
Это отдельный поток от выпуска карты и пополнения карты.

- **Покупки в магазине (веб)**: сбор определяется настройками тарифа и индивидуальной ценой аккаунта.
- **Заказы через Open API**: взимается сервисный сбор за заказ; он удерживается при создании заказа,
  списывается при успехе и освобождается при терминальном состоянии, при котором списания точно не было.
- **CDK**: сервисный сбор взимается при выпуске кода; выпуск карты, фондирование и оплата подписки при
  активации финансируются **владельцем CDK**.
- Для GPT цена подписки у апстрима **не** фиксирована в USD. Сначала вызовите preflight, чтобы получить
  актуальную котировку для текущего региона, валюты и состояния аккаунта.

**Откуда брать учётные данные Grok** (это не пароль x.ai и не привязка X)

начинающийся с `eyJ`. Это **не** пароль аккаунта x.ai, **не** шаг «привяжите X, чтобы получить

Передавайте так:

"credential": { "mode": "session", "session": "eyJ..." }

Подойдёт и полная строка Cookie, если в ней есть `sso=`.

#### ★Четыре ловушки, которых нужно избежать★

Все четыре — реальное поведение. Ни одна не выдаёт ошибку: они просто дают неверный результат.

**Ловушка 1: опечатка в `product` не отклоняется — значение трактуется как `gpt`.**

При создании заказа неизвестный `product` **молча приводится к `gpt`**. Напишите `cluade` вместо
`claude` — и вы создадите **заказ GPT с реальным списанием**, а не получите ошибку валидации.

> ★Проверяйте `product` на своей стороне★ и разрешайте только литералы `gpt`, `claude`, `grok`.
> Не рассчитывайте, что сервер вас остановит.

Аналогично `GET /gpt-direct/plans?product=<неизвестное>` возвращает **все тарифы всех трёх продуктов**
(а `registry` — пустой массив), а не ошибку. Если в `plans` рядом с `plus` появились `claude_pro` и
`grok_monthly`, значит ваш `product` не подействовал.

**Ловушка 2: ключи в `plans` отличаются от `registry[].key` — совпадают только у GPT.**

| `product` | Ключ в `plans` | `registry[].key` | Что передавать в `plan` |
| --- | --- | --- | --- |
| `gpt` | `plus` | `plus` | `plus` (совпадают) |
| `claude` | `claude_pro` | `pro` | **`pro`** |
| `grok` | `grok_lite_monthly` | `lite_monthly` | **`lite_monthly`** |

У Claude и Grok ключи в `plans` содержат префикс продукта, а в `registry` — нет.
**В `plan` передавайте `registry[].key`** (без префикса). Если применить к Claude ту же логику, что
вы вывели на GPT, и передать ключ из `plans`, получите «неизвестный тариф».

**Ловушка 3: Claude / Grok — фиксированная цена в USD, не наследуйте филиппинский дефолт GPT.**

Витрина Claude всегда идёт в `US/USD`. Если регион не передан, Open API для GPT по умолчанию
ставит `PH/PHP`. Если применить это к Claude / Grok, сервер сравнит долларовую цену с песо и
вернёт «тариф не настроен или валюта не совпадает» — выглядит как «цена не сконфигурирована»,
хотя цена уже есть.

- Передавайте `"product": "claude"` (или `grok`) и запрашивайте планы с `?product=…`.
- В `plan` отправляйте `registry[].key` (например `max_5x`), не ключ из `plans` с префиксом.
- Цену читайте из `registry[].checkout_amount_minor` (центы USD).
- **Явно передавайте** `"payment_country":"US","payment_currency":"USD"`.
  Новые сборки и без этого упадут на US; старые без параметров уйдут в PH и отклонят заказ.

```bash
# SuperGrok (месяц). session = cookie sso с grok.com
curl -X POST https://zovocard.com/openapi/v1/gpt-direct/orders \
  -H "X-API-Key: sk_your_key" -H "Content-Type: application/json" \
  -d '{
    "product": "grok",
    "plan": "monthly",
    "payment_country": "US",
    "payment_currency": "USD",
    "card_id": 12345,
    "credential": {"mode": "session", "session": "eyJ..."},
    "client_request_id": "your-unique-id"
  }'
```
- Для GPT по-прежнему действует дефолт `PH/PHP`.

**Ловушка 4: `enabled`, `purchasable` и наличие в `registry` — три разных переключателя, не одно состояние.**

Поля `purchased` нет. В документации и ответе имя — **`purchasable`**.
`plans[<key>].enabled === true` означает только, что ACC знает этот тариф — **не** что его
сейчас можно купить или выпустить CDK.

| Поле | Кто управляет | Смысл |
| --- | --- | --- |
| Есть ли тариф в `registry` | Витрина карточной платформы | Невыложенный тариф в `registry` не появляется |
| `registry[].purchasable` | Реестр платформы | **Можно ли купить сейчас.** `false` = всё ещё видно, серым «скоро», заказ / выпуск CDK отклоняется |
| `plans[<acc_plan_key>].enabled` | Исполнение ACC | Примет ли апстрим погашение. В `plans` смотрите по `registry[].acc_plan_key` (у Claude / Grok ключи с префиксом) |

**Продавать можно тогда и только тогда, когда выполнены все три условия:**

```text
тариф есть в registry
AND registry[].purchasable === true
AND plans[registry[].acc_plan_key].enabled === true
```

`enabled=true` и `purchasable=false` = тариф выложен, ACC включён, но платформа ещё не открыла
продажу. Коды не выпускайте.

#### 6.18.0.1 Своя карта (`raw_card`) — ★только Open API★

Оплата вашей собственной картой, минуя выбор карты платформы, проверку баланса и фондирование.

| Параметр | Тип | Примечание |
| --- | --- | --- |
| `raw_card` | string | `номер\|месяц\|год\|CVV`, например `4111111111111111\|12\|30\|123`. Год — 2 или 4 цифры |

- `card_id` и `raw_card` **взаимоисключающие**: нужен ровно один. Передача обоих даёт
  `INVALID_REQUEST` — какую карту списывать, не должно быть двусмысленности.
- Требует включённой функции на платформе, иначе `403 EXTERNAL_CARD_DISABLED`.
- **Взимается сбор за заказ** с баланса платформы: GPT `$0.30`, Claude `$10.00` (приоритет — настройка
  платформы). Сбор `0` означает, что продукт **не** поддерживает свои карты, а не что это бесплатно.
- Такие заказы не фондируются платформой и не расходуют квоту прямых пополнений карты. Недостаток
  средств на вашей карте приводит к отказу со стороны апстрима.

#### 6.18.1 Право доступа и сервисные сборы

Нужен действующий `app_secret`, а также: активный **мастер-аккаунт** без ограничений по картам, хотя бы
один зачисленный депозит (кроме администраторов) и **любое одно** из:

1. Прямое пополнение включено администратором вручную;
2. Аккаунт администратора;
3. Super / Supreme / Legend SVIP и выше.

При достижении порога VIP доступ открывается автоматически. **Субаккаунт может использовать GPT Direct со своим действующим API-ключом.** Основной аккаунт должен соответствовать указанным выше требованиям и иметь зачисленный депозит. Оба аккаунта должны быть активны, без ограничений по картам; действующая связь должна предоставлять право `gpt_direct`. Отдельно включать `gpt_direct_enabled` у субаккаунта не нужно. Отзыв права или заморозка связи сразу блокирует доступ. При недоступности сервиса операции записи могут завершаться ошибкой.

Выпуск одной или нескольких карт через `POST /cards/open` и `POST /cards/batch-open` требует отдельного права `open_card`. Карты, заказы и обычные списания за выпуск или прямое пополнение остаются у субаккаунта; расходуется его выделенный баланс. Средства основного аккаунта не разрешают овердрафт субаккаунта. Не передавайте ему API-ключ основного аккаунта.

> **Продление Pro 20x (`pro_20x_renew`) — тариф с привязкой карты, семантика отличается от всех остальных**
> - Он **не покупает подписку**. Он привязывает фондированную карту к аккаунту, **который уже
>   находится на Pro 20x**, и делает её картой по умолчанию. OpenAI спишет с этой карты в свою
>   дату продления, поэтому **сам заказ не вызывает списания у апстрима** — нет котировки
>   preflight и нет проверки суммы платежа. Взимается только сервисный сбор API / CDK.
> - **Целевой аккаунт должен сейчас быть на Pro 20x.** Иначе заказ отклоняется на этапе
>   **preflight** и не создаётся:
>   - `GPT_RENEW_TARGET_NOT_PRO` — аккаунт не на Pro 20x (Pro 5x / Plus / Free и т. д.)
>   - `GPT_RENEW_SUBSCRIPTION_EXPIRED` — был на Pro 20x, но подписка истекла; это считается новой
>     подпиской, а не продлением
>
>   Обе ошибки **детерминированы**: повтор с другой картой не поможет. Используйте тариф нового
>   оформления или повышения.
> - Карта, выпущенная под заказ продления, закрепляется за ним **монопольно** и не переиспользуется.
> - Успех означает только «карта привязана и назначена по умолчанию» — он **не означает**, что
>   подписка продлена. Фактическое списание произойдёт в собственном цикле продления OpenAI,
>   поэтому оставьте на карте достаточно средств для оплаты счёта Pro.
> - **Без пострановой цены**: заказ продления ничего не списывает, поэтому `payment_country` / `payment_currency` для него не важны; регион оплаты влияет только на новые тарифы, апгрейд и кредиты.

> **Кредиты Codex (`credit250` / `credit500` / `credit1000` / `credit2500` / `credit5000` / `credit25000`)**
> - Кредиты — это **дополнение** к подписке: у целевого аккаунта уже должна быть активная подписка
>   Plus/Pro, иначе заказ отклоняется (`GPT_CREDIT_REQUIRES_SUBSCRIPTION`). Бесплатный аккаунт не
>   сможет использовать купленные кредиты.
> - Кредиты **не меняют тариф**, поэтому один и тот же аккаунт может покупать их многократно и не
>   будет заблокирован по причине «подписка ещё активна».
> - Оплата идёт в PHP, а карта рассчитывается в USD, поэтому фактическая сумма в USD зависит от
>   дневного курса. Платформа фондирует карту по реальному дневному курсу с защитной маржой
>   (по умолчанию 12%) и округлением вверх; излишек возвращается при удалении карты.
> - Заказы на кредиты не расходуют квоту прямых пополнений карты.

#### 6.18.3 Preflight учётных данных

`POST /gpt-direct/preflight`

| Поле | Примечание |
| --- | --- |
| `product` | Опционально; `claude` / `grok` идут по своим путям, всё остальное — GPT |
| `plan` | Опционально |
| `credential` | GPT: session / почта. Claude: `sk-ant-…`. **Grok: cookie `sso` с grok.com** в `credential.session` с `mode: "session"` |
| `session` | Legacy; предпочтительнее `credential` |
| `payment_country` / `payment_currency` | Опционально. GPT по умолчанию PH/PHP; для Claude / Grok передавайте `US`/`USD` |

Возвращает состояние аккаунта, `preflight_token` и `preflight_expires_at`, текущий тариф, причины
блокировки и котировки. **`preflight_token` обязателен для заказов GPT**, если preflight не встроен в
запрос. Для Claude и Grok он не нужен.

- Лимит: **60/мин на пользователя и 120/мин на IP**; при превышении —
  `429 GPT_PREFLIGHT_RATE_LIMITED`.
- Preflight Grok (`"product":"grok"`) проверяет cookie `sso` и текущую подписку.
  Билет **не выдаёт**; при создании заказа `credential.session` всё равно нужен.

| `product` | string | нет | По умолчанию `gpt` — см. Ловушку 1. Для Claude / Grok обязательно |

| `credential` | object | **да** | Сессия GPT / Claude `sk-ant-…` / **cookie `sso` grok.com** |

#### 6.18.5 Запрос, детали и отмена

- `GET /gpt-direct/orders` — `page`, `page_size` (макс. 100). Только заказы, созданные через **этот API**.
- `GET /gpt-direct/orders/{id}` — заказ и публичная лента `events`. `404`, если это не ваш заказ,
  созданный через API.
- `POST /gpt-direct/orders/{id}/cancel` — только до начала оплаты, иначе `409`.
- `POST /gpt-direct/orders/{id}/cancel-renewal` — отменяет автопродление у GPT-аккаунта этого заказа.
  Право пользования сохраняется до конца текущего периода; **это не возврат средств**.

**Машина состояний заказа (определяйте ошибку только по ней)**

| Класс | Статус | Значение |
| --- | --- | --- |
| В процессе | `queued` / `awaiting_card` / `funding_pending` / `dispatching` / `running` | В очереди / выбор карты / фондирование / отправка — продолжайте опрос |
| В процессе | `requires_action` / `pending` / `plus_paid` | Нужен 3DS / ожидание подтверждения подписки / Plus оплачен, идёт апгрейд — **не повторять** |
| Ожидает сверки | `review` | Результат оплаты на ручной проверке — **не повторять** |
| **Терминальный** | `completed` | Целевой тариф активирован (успех) |
| **Терминальный** | `declined` / `failed_precharge` / `cancelled` | Окончательная ошибка / отмена |

**Про `declined` и автоматическую смену карты.** Автосмена карты включена по умолчанию (до 2 попыток):
если по одной карте пришёл отказ, заказ **меняет карту и возвращается в `queued`**. Такой промежуточный
отказ **не** переводит заказ в `declined` и **не** вызывает вебхук `gpt_direct.failed` — он виден лишь
как `queued↔dispatching` в событиях `gpt_direct.progress`. Только реальная ошибка после исчерпания всех
попыток переводит заказ в `declined`.

> ★Поэтому считайте ошибкой только★: статус `declined` / `failed_precharge` / `cancelled`, прочитанный
> из заказа, либо вебхук `gpt_direct.failed` / `gpt_direct.cancelled`.
> **Никогда** не показывайте пользователю промежуточную постановку в очередь или повтор как ошибку.
> Передайте `no_auto_card_switch=true`, чтобы отключить смену карты — тогда первый отказ терминален.

> Для путей апгрейда GPT `completed` не всегда означает, что подписка уже активна — проверяйте также
> `stage` и `user_message`.

#### 6.18.5a Правила карт, остаток использований, предпросмотр пула

По умолчанию всё как сейчас: **неудачи и отмены считаются**, 5 обычных / 3 Pro 20x на карту, выбор по балансу, автосмена до 2 раз. Партнёр может менять это по продукту (`gpt` / `claude` / `grok`) и сам сбрасывать отметки неудач. Платформа **не** перешла на «считать только успех».

Счётчики — **на карту** (общие для продуктов). Правило только задаёт, как этот продукт читает карту.

- `GET /gpt-direct/card-rules` — без `product` вернёт все три (пустые строки заполняются умолчаниями, `is_default=true`)
- `PUT /gpt-direct/card-rules` — `product`, `count_failures`, `light_max_uses` (`0` = без лимита), `pro20_max_uses`, `select_mode` (`default` / `lowest_usage` / `newest`), `auto_switch_on_fail`, `max_auto_switches`
- `GET /gpt-direct/cards/{id}/usage?product=gpt` — остаток; `remaining=-1` = без лимита
- `POST /gpt-direct/cards/reset-usage` — `{ "card_ids": [101], "scope": "failed" }`; пустой `card_ids` = все ваши карты; `scope=all` также сбрасывает успехи. Текущие резервы не трогаются
- `GET /gpt-direct/card-pool/schedule?product=gpt&plan=plus&card_mode=auto_existing` — предпросмотр выбора карты без создания заказа
- `GET /gpt-direct/card-products` — продукты карт и флаг `usable`
- `PUT /gpt-direct/card-rules` также принимает `select_priority` и `strict_select`

Те же пути в магазине: `/api/v1/gpt/direct/`.

#### 6.18.5b Заказы аккаунта: чтение и синхронизация, включая mall

- `GET /gpt-direct/account-orders`: все источники (`mall` / `api` / `cdk`) **аккаунта владельца API Key**, независимо от ключа, создавшего заказ. Заказы других, родительских и дочерних аккаунтов не объединяются. Сохраняются проверки доступа OpenAPI/GPT Direct, списка разрешённых IP и наличия пополнения.
- `GET /gpt-direct/account-orders/{id}`: та же безопасная сводка; чужой заказ возвращает `404`. Только чтение, без отмены, активации или экспорта учётных данных.
- Старый `/gpt-direct/orders` по-прежнему ограничен заказами владельца с `source=api`, а не только текущим ключом.

Префикс: `/openapi/v1`, авторизация: `X-API-Key`. Параметры списка: `page_size` — 20 по умолчанию, от 1 до 100; необязательный `source=mall|api|cdk`, без него все источники; `updated_after` — время RFC3339 с часовым поясом, **включая границу**. Неизвестные/повторные параметры, неверные даты и курсоры возвращают `400`.

Пагинация курсорная, параметр `page` не поддерживается. Фильтры задаются в первом запросе; далее передавайте только `cursor=<next_cursor>` и при необходимости `page_size`, без `source` / `updated_after`. Сортировка по `(updated_at, order_id)` по возрастанию; `sync_until` фиксируется на весь обход. `has_more=false` завершает обход, полного подсчёта строк нет.

Для инкрементальной синхронизации сначала прочитайте все страницы и сохраните `sync_until`. Следующий `updated_after` задавайте с перекрытием (рекомендуется минимум 5 минут); обновляйте запись по `order_id`, игнорируя более старый `updated_at`. Это изменяемый снимок заказов, не неизменяемый журнал событий: параллельные и поздние фиксации транзакций требуют повторного чтения. Периодически перепроверяйте незавершённые заказы. Продвигайте отметку синхронизации только после всех страниц. Список не создаёт Webhook `event_id`; повторы вебхуков удаляются по их стабильному `event_id`.

Возвращаются только поля ниже. Email маскируется, номер карты содержит лишь последние четыре цифры (`""`, если недоступны). Полные номера карт, CVV, Session, учётные данные, платёжные ссылки и прокси не возвращаются. Суммы в минимальных единицах валюты платежа; котировка и итоговая сумма сами по себе не подтверждают оплату. Все три времени — RFC3339 UTC; `completed_at=null`, пока время завершения не записано.

```http
GET /openapi/v1/gpt-direct/account-orders?source=mall&page_size=20&updated_after=2026-09-24T00%3A00%3A00Z
X-API-Key: YOUR_API_KEY
```

```json
{"code":0,"msg":"ok","data":{"list":[{"order_id":981,"source":"mall","product":"gpt","plan":"plus","account_email":"us***@example.com","status":"completed","stage":"completed","quoted_amount_minor":98000,"final_amount_minor":98214,"currency":"PHP","card_id":456,"card_last_four":"1234","created_at":"2026-09-24T10:00:00Z","updated_at":"2026-09-24T10:05:00Z","completed_at":"2026-09-24T10:05:00Z"}],"next_cursor":"","has_more":false,"sync_until":"2026-09-24T10:06:00Z"}}
```

Порядок подключения: настройте общий вебхук и сохраняйте входящие события до первого полного обхода заказов аккаунта. Затем опрашивайте изменения через `updated_after`. Удаляйте повторы по `event_id`, объединяйте записи по `order_id` и не перезаписывайте новое состояние более старым `updated_at`. Проверка одного заказа: `GET /openapi/v1/gpt-direct/account-orders/{id}`; `data` содержит саму сводку заказа, без учётных данных или хронологии.

#### 6.18.6 Выпуск и поиск CDK

Относительные пути ниже используют `/openapi/v1` и API-ключ владельца на вашем сервере. При выпуске списывается сервисная комиссия; пополнение карты и подписку при активации оплачивает владелец CDK. Актуальную цену берите из `GET /gpt-direct/plans`, не считайте комиссию всегда нулевой.

`POST /gpt-direct/cdks`:

```json
{"plan":"plus","count":2,"funding_confirmed":true,"payment_country":"PH"}
```

| Поле | Условия |
| --- | --- |
| `plan` | Обязательно: `go`, `plus`, `pro_5x`, `pro_20x`, `pro_50x`, `pro_20x_renew`, `credit250`, `credit500`, `credit1000`, `credit2500`, `credit5000`, `credit25000`; тариф должен быть доступен для покупки |
| `count` | По умолчанию 1; рекомендуются 1–200. Максимум **200** кодов |
| `funding_confirmed` | Обязательно `true`: согласие владельца оплатить активацию |
| `payment_country` | PH / US / JP / CL / EG согласно `payment_regions` в `/gpt-direct/plans`; по умолчанию PH |
| `payment_currency` | Можно опустить: определяется по стране. Если передана, должна соответствовать стране |
| `preferred_issuer` / `preferred_segment_type` / `preferred_segment_key` | Снимок предпочтений для отображения; **не привязывает карту и не определяет последующий выбор** |

- Весь пакет выпускается в одной транзакции: либо все коды, либо полный откат. Ответ: `data.requested`, `data.issued[]` с `id/code/code_prefix/plan/fee_amount_minor` (центы USD).
- Передавайте уникальный `Idempotency-Key`; при повторе сохраняйте ключ и тело. При неизвестном результате сначала проверьте список кодов, не покупайте повторно с новым ключом.
- Сохраняйте полный `code`. Список владельца также возвращает сохранённый открытый код; у старых записей только с хешем его может не быть. Префикс не подходит для активации; поддерживайте новые и старые длины кодов.
- Запрос выпуска **не принимает** `owner_funding_cap_minor`. Новые покупки не устанавливают жёсткий лимит; для существующих кодов действуют сохранённые разрешения. `preview.funding_cap_minor=0` означает отсутствие лимита.
- `pro_20x_renew` привязывает карту продления подходящему аккаунту Pro 20x, без списания подписки в этом процессе. Оставьте средства для будущего счёта. Пакеты кредитов требуют действующей Plus/Pro; предварительная проверка обязательна.

| Метод и путь | Запрос и ответ |
| --- | --- |
| `GET /gpt-direct/cdks` | `page/page_size` (обычно20, максимум200), `status/plan/q`; `data.list/total`. Коды этого ключа и покупки на сайте без привязки App |
| `POST /gpt-direct/cdks/{id}/disable` | Отключить неиспользованный код своего аккаунта; `data.id/status`, без возврата комиссии выпуска |
| `POST /gpt-direct/cdks/{id}/enable` | Восстановить подходящий код аккаунта в `unused` |
| `POST /gpt-direct/cdks/batch-disable` | `{"ids":[101,102]}`, максимум100; массивы ID `data.disabled/failed` и счётчики |
| `POST /gpt-direct/cdks/batch-enable` | Аналогично, успешные ID и число — `enabled/enabled_count` |

Пакетное включение/отключение обрабатывает элементы отдельно: проверяйте `failed` даже при HTTP 200. Списки и заказы фильтруются по Key/App; включение/отключение проверяет владельца аккаунта. Разные ключи одного аккаунта не изолируют эти права.

Статусы CDK: `unused` — доступен; `reserved` — связан с активным заказом; `consumed` — использован; `review` — удержан для проверки; `frozen` — заморожен; `disabled` — отключён.

##### Собственный префикс бренда CDK

Сохраните сокращение бренда в разделе **Мои CDK → Префикс бренда CDK** или через серверные интерфейсы ниже. Аккаунту нужен доступ к GPT direct, а также выполнение требований к пополнению и правам субаккаунта. Запросы настроек не обращаются к платёжному провайдеру.

| Метод и полный путь | Назначение |
| --- | --- |
| `GET /openapi/v1/gpt-direct/cdk-branding` | Прочитать префикс текущего аккаунта и примеры по тарифам |
| `PUT /openapi/v1/gpt-direct/cdk-branding` | Сохранить префикс текущего аккаунта |

Оба метода используют `X-API-Key`. Пример тела PUT:

```json
{"brand_prefix":"UUU"}
```

Успешный ответ: `code=0`, в `data` — `brand_prefix`, `plan_labels` и `examples`. Например, `plan_labels.plus="PLUS"`, `examples.plus="UUUPLUS-XXXXXXXXXX-XXXXXXXXXX"`. Символы X обозначают пример, а не код для активации.

- Допустимы 1–8 латинских букв ASCII или цифр, первый символ — буква. Буквы переводятся в верхний регистр. Пробелы, дефисы и HTML запрещены. `{"brand_prefix":""}` восстанавливает стандартный формат; поле нельзя пропускать или передавать как null. Неверное значение возвращает HTTP 400 и `error_code=cdk_brand_prefix_invalid`.
- Для `UUU`: Plus — `UUUPLUS-…`, Pro 5x — `UUU5X-…`, Pro 20x — `UUU20X-…`, Pro 50x — `UUU50X-…`, привязка карты для продления — `UUU20XRENEW-…`, Go — `UUUGO-…`, пакеты кредитов — `UUUC250-…` / `UUUC500-…` / `UUUC1000-…`. Случайная часть по-прежнему состоит из двух групп по 10 шестнадцатеричных символов.
- Настройка применяется к новым одиночным/пакетным покупкам на сайте, выпуску через API и выдаче администратором для этого аккаунта. Все его API Key используют одну настройку; основной аккаунт и субаккаунты настраиваются отдельно. Параметры подмены `user_id/owner_id/api_key_id` не принимаются. Поля запроса выпуска не меняются: не добавляйте `brand_prefix` в запрос покупки.
- Без настройки или после её очистки сохраняется формат `ZC-…`. Ранее выданные коды не меняются и активируют исходный тариф. Определяйте тариф по полю `plan`, а не по префиксу. `code_prefix` — только сокращённый фрагмент; храните и передавайте полный `code`, не фиксируя длину или префикс.
- PUT поддерживает существующий необязательный `Idempotency-Key`: повтор запроса — тот же ключ и тело, другое значение настройки — новый ключ. Сохранение бесплатно и не выпускает, не активирует и не возвращает коды.

После подтверждения оплаты, в том числе при исправлении статуса по операции карты, CDK получает статус `consumed`: повторная активация, включение и удаление с возвратом комиссии запрещены. Неудачная попытка внутри выполняющегося процесса не является окончательным отказом заказа. Пока обработка или подтверждение платежа продолжается, проверяйте исходный заказ и не активируйте код повторно.

#### 6.18.7 Сверка CDK-заказов

- `GET /gpt-direct/cdk-orders` — фильтры `updated_after` (RFC3339), `status`, `cdk_id`, `order_id`,
  `page`, `page_size` (макс. 100).
- `GET /gpt-direct/cdk-orders/{order_id}` — один заказ и его публичная лента `events`.

В результатах есть префикс и статус CDK, маскированные аккаунт и номер карты, суммы, состояние
сервисного сбора и фондирования, стадия заказа и временные метки. Учётные данные, прокси, внутренняя
диагностика, полные коды CDK и полные номера карт не возвращаются никогда. Видимость как у списка
кодов (этот ключ плюс купленные на сайте и не привязанные к приложению). Заказы другого ключа скрыты.
Для кодов с сайта webhook на позже созданный ключ не уходит — сверяйте `cdk-orders`.


Список и детали CDK-заказов содержат `renewal_status` (добавлено 2026-09-25), отдельно от платёжного `status`. `success` — система зафиксировала отмену продления; `pending/retrying` — обработка продолжается; `warning/manual_required` — нужна проверка или ручная обработка; `not_requested` — отмена для этого заказа не запрашивалась (например, `pro_20x_renew` сохраняет автопродление). Пустое значение означает неизвестный результат, а не успех. После `completed` можно продолжать чтение статуса; ожидание отмены не является причиной повторной активации или оплаты. Такой запрос не отправляет новую команду отмены.

#### 6.18.8 Активация CDK (публичные эндпоинты, без API-ключа)

Base: `https://zovocard.com/api/v1/cdk`. API-ключ не нужен; полный действительный код создаёт краткосрочную сессию. Сохраняйте исходящий IP и `X-Redemption-Device`; без заголовка используется `User-Agent`.

Лимиты публичных запросов по IP: preview 30/мин, redeem 20/мин, result 60/мин. Preflight также ограничен; при HTTP 429 увеличивайте интервал повторов.

**Асинхронный приём (2026-09-24):** заказ, резерв CDK, использование preflight и привязка сессии результата фиксируются одной транзакцией до ответа. Выбор карты, финансирование и оплата продолжаются в фоне. Сохраняются HTTP 200, `code=0`, `data.id`; переходить на HTTP 202 не требуется. Новый заказ имеет `status=awaiting_card`, `stage=cdk_accepted`; `card_id` может отсутствовать/быть 0. Продолжайте опрос. После перезапуска обработка восстанавливается из БД.

При повторе сохраняйте `redemption_token/preflight_token/client_request_id` и параметры выбора. Идентичный запрос возвращает исходный заказ; изменённые параметры — 409 `IDEMPOTENCY_CONFLICT`. Приём не означает успех оплаты: нехватка средств/разрешений в фоне отражается в статусе и событиях.

```json
{"code":0,"msg":"ok","data":{"id":456,"status":"awaiting_card","stage":"cdk_accepted","async_card_selection":true}}
```


| Шаг | Метод и полный путь | Запрос и результат |
| --- | --- | --- |
| 1. Preview | `POST /api/v1/cdk/preview` | `{"code":"<full CDK>"}` → `data.redemption_token/expires_at/plan/plan_flow/funding_cap_minor`; сессия 15 минут |
| 2. Preflight | `POST /api/v1/cdk/preflight` | `redemption_token` + `credential` → `data.preflight_token/preflight_expires_at`, проверка и цена; регион берётся из кода |
| 3. Активация | `POST /api/v1/cdk/redeem` | `redemption_token/preflight_token/client_request_id` → `data.id/status/stage` |
| 4. Результат | `GET /api/v1/cdk/result?token=<redemption_token>` | `data.order/events`; прежняя привязка IP/устройства |

```json
{"redemption_token":"<preview token>","credential":{"mode":"session","session":"<customer session>"}}
```

На шаге 3 не повторяйте credentials. `exclude_card_ids` исключает карты для заказа; `strict_card_preference=true` отключает резервные сегменты платформы; `no_auto_card_switch=true` отключает автоматическую замену. Выбор использует **текущие правила владельца**, а при их отсутствии — настройки платформы, не снимок `preferred_*` при выпуске.

Конкретная карта задаётся через §6.18.8a. Публичный маршрут отклоняет ненулевой `card_id`:403 `CARD_SELECTION_REQUIRES_API_KEY`.

При `queued/awaiting_card/funding_pending/dispatching/running/requires_action/pending/plus_paid` и review продолжайте проверку без повторной оплаты. `completed` означает завершение процесса тарифа; привязка карты продления не означает оплату следующего счёта. `declined/failed_precharge/cancelled` — конечные статусы заказа, но **не доказательство возврата денег или освобождения кода**. Проверяйте `cdk_status/funding_hold_status/service_fee_status` и события через API владельца. Повторно активируется только `unused`; подтверждение списания или неопределённость могут сохранить `review`.

Публичный результат включает `data.order.card_id/card_last_four`. Последние цифры могут отсутствовать и не уникальны; по ним нельзя определять успех. Не помещайте API-ключи и Session в исходный код страницы или журналы.

#### 6.18.8a Выбор существующей карты при активации CDK (API владельца)

`POST /openapi/v1/gpt-direct/cdks/redeem` требует API Key владельца и активирует купленный CDK без повторного списания предоплаченной комиссии. При покупке, выпуске и хранении CDK карта не привязывается.

Активация владельцем без `card_id` использует тот же асинхронный приём. Явно выбранная карта проверяется и фиксируется до ответа, без перехода к автоматическому выбору.

Вызовите публичные `/api/v1/cdk/preview` и `/preflight` **с вашего сервера**, затем этот метод с тем же исходящим IP и `X-Redemption-Device`. Не размещайте API Key в браузере покупателя. Доступны только CDK данного владельца, выпущенные текущим ключом, и купленные на сайте CDK без привязки к App.

```json
{"redemption_token":"<preview>","preflight_token":"<preflight>","client_request_id":"redeem-example-001","card_id":123}
```

- `card_id` — необязательный локальный ID карты. Отсутствие/0 сохраняет автоматический выбор. Указанная карта фиксируется: автоматическая замена и выпуск другой карты запрещены, в том числе при повторных попытках.
- Карта должна принадлежать владельцу CDK, быть ACTIVE и не просрочена; не должно быть незавершённого пополнения, возврата или удаления. Сохраняются лимиты использования, охлаждение, архивирование, доступность канала и эксклюзивность карты продления.
- При недостатке средств существующий процесс пополняет только указанную карту в пределах разрешения владельца, лимита CDK и доступного баланса. Средства с других карт не возвращаются для финансирования операции.
- Это новая ручная активация, а не автопродление. Условия подписки и `pro_20x_renew` не меняются. Ошибка проверки карты не расходует CDK/предпроверку; неопределённый результат остаётся на сверке.
- Идемпотентность задаётся обязательным `client_request_id`. При повторе сохраните CDK, карту, токен предпроверки и параметры выбора; изменение возвращает `409 IDEMPOTENCY_CONFLICT`. Общий кеш ответа `Idempotency-Key` для этого метода не используется.
- Поддерживаются `exclude_card_ids`, `strict_card_preference`, `no_auto_card_switch`. Карта в списке исключений отклоняется; false не отменяет фиксацию карты.

Ответ: `data.order` с `order_id`, `card_id`, `card_last_four`, статусами заказа и финансирования, плюс `data.events`. Последующие запросы — §6.18.7. Публичный `/api/v1/cdk/result` также возвращает `order.card_id` / `order.card_last_four`, без полного номера карты/CVV.

Коды отказа: `CARD_NOT_FOUND`, `CARD_NOT_PAYABLE`, `CARD_EXPIRED`, `CARD_DETAILS_UNAVAILABLE`, `CARD_FUNDING_BUSY`, `CARD_IN_USE`, `CARD_CAPACITY_REACHED`, `CARD_CAPACITY_PRO20`, `CARD_RENEWAL_BOUND`, `CARD_COOLING_DOWN`, `CARD_PLAN_UNSUPPORTED`, `CARD_SELECTION_LOCKED`. Публичный `/api/v1/cdk/redeem` при ненулевом `card_id` возвращает `403 CARD_SELECTION_REQUIRES_API_KEY`.

**Параметры и последовательность**

Обязательны `redemption_token/preflight_token/client_request_id`; ID запроса — 1–80 байт (рекомендуется ASCII). `card_id` — положительный целочисленный **локальный ID карты**, не PAN, последние цифры или строковый ID эмитента. Сохраните `order.card_id` из предыдущего `cdk-orders/{order_id}` либо возьмите ID из списка своих карт.

Выполняйте запросы на своём сервере, передавая полученные токены в следующий шаг и сохраняя IP/устройство. При покупке и выпуске кода `card_id` не передаётся.

```bash
# Server-side only. Set these variables privately; never ship the key to a browser.
ZOVOCARD_ORIGIN='https://sandbox.zovocard.com'
# Production: https://zovocard.com with a separate production key.
curl --fail-with-body "$ZOVOCARD_ORIGIN/api/v1/cdk/preview" \
  -H 'Content-Type: application/json' -H 'X-Redemption-Device: merchant-session-001' \
  -d '{"code":"<full CDK>"}'

curl --fail-with-body "$ZOVOCARD_ORIGIN/api/v1/cdk/preflight" \
  -H 'Content-Type: application/json' -H 'X-Redemption-Device: merchant-session-001' \
  -d '{"redemption_token":"<preview token>","credential":{"mode":"session","session":"<customer session>"}}'

curl --fail-with-body "$ZOVOCARD_ORIGIN/openapi/v1/gpt-direct/cdks/redeem" \
  -H "X-API-Key: $ZOVOCARD_API_KEY" -H 'Content-Type: application/json' \
  -H 'X-Redemption-Device: merchant-session-001' \
  -d '{"redemption_token":"<preview token>","preflight_token":"<preflight token>","client_request_id":"merchant-redeem-001","card_id":123}'

# Use data.order.order_id returned above.
curl --fail-with-body "$ZOVOCARD_ORIGIN/openapi/v1/gpt-direct/cdk-orders/456" \
  -H "X-API-Key: $ZOVOCARD_API_KEY"
```

Пример успеха (основные поля; HTTP 200 означает создание заказа, **не завершение оплаты**):

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "order": {
      "order_id": 456,
      "client_request_id": "merchant-redeem-001",
      "cdk_id": 78,
      "cdk_status": "reserved",
      "status": "queued",
      "card_id": 123,
      "card_last_four": "1234"
    },
    "events": []
  }
}
```

Сохраните `data.order.order_id/card_id/card_last_four` и подтвердите карту по конечному результату. Полные PAN/CVV не возвращаются. Если карта недоступна, не подменяйте её `card_id=0` и не создавайте обычный заказ прямого пополнения.

| HTTP / error_code | Действие |
| --- | --- |
| 409 `IDEMPOTENCY_CONFLICT` | ID уже связан с другими параметрами; сначала найдите исходный заказ |
| 403 `CDK_NOT_ACCESSIBLE` | Проверьте владельца и Key/App выпуска |
| 400 `REDEMPTION_SESSION_INVALID` | Проверьте срок/IP/устройство. Перед новым preview/preflight убедитесь, что заказ не создан |
| 400 `CDK_UNAVAILABLE` | Код использован или обрабатывается; запросите существующий заказ |
| 400 `CARD_*` / `REDEMPTION_REJECTED` | Исправьте состояние, принадлежность, лимит, cooldown или разрешение на финансирование; без автоматической замены |

Действуют аутентификация, IP allowlist, права Direct и субаккаунта. Ваш сервер также проверяет личность клиента и разрешённую ему карту: ID из браузера не является разрешением. Если старая версия вернула 404, подтвердите поддержку у платформы, не переключайтесь на автоматический выбор.

### 6.19 Отмена автопродления по сессии (любой аккаунт)

`POST /gpt-direct/cancel-renewal`

Отменяет автопродление для **любого** GPT-аккаунта, используя только полную Session — **id заказа не
нужен**.

Вариант из §6.18.5 работает только с заказами, созданными через этот API, поэтому существующие
аккаунты (оформленные в веб-консоли или полученные иначе) нельзя было обработать. Здесь критерий
меняется с «кому принадлежит заказ» на «у кого есть Session».

```bash
curl -X POST https://zovocard.com/openapi/v1/gpt-direct/cancel-renewal \
  -H "X-API-Key: sk_ваш_секрет" \
  -H "Content-Type: application/json" \
  -d '{"session":"<полный Session JSON или sessionToken>"}'
```

Возвращает `renewal_status`, `renewal_message`, `email`, а при наличии — `will_renew`, `active_until`,
`returned_amount`, `plan_type`. При ошибке — 400. Запись заказа не обновляется.

| `renewal_status` | Значение | Результат повторного вызова |
|---|---|---|
| `success` | Отменено | Идемпотентно; к апстриму повторно не обращаемся |
| `pending` | Принято апстримом, не подтверждено | Повторяет отмену |
| `warning` | Попытка была, нужна проверка | Повторяет отмену |
| `not_requested` | Апстрим не запрашивался (например, оплата не прошла) | HTTP `409` |

### 6.20 Публичные запросы вашего собственного CDK-сайта

Сверено с исходным кодом `zovo_card_cdk_auto` **v1.4.22**. Маршруты находятся на вашем домене, например `https://cdk.example.com`, **не** на `/openapi/v1` или `/api/v1/cdk/*` платформы.

Шаблон пока пересылает `/api/v1/public/cdk/redeem` в публичную активацию платформы, а не в API владельца с фиксированной картой. Добавить `card_id` недостаточно: адаптируйте свой сервер по §6.18.8a. Публичные запросы ниже не требуют API-ключа платформы, но полный CDK/Session — секрет доступа.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/v1/public/cdk/plans` | Корневые `source/plans/registry/version`; актуальные данные: `cardplatform_live`; `docs_default/docs_default_fallback` — справочные цены |
| `POST /api/v1/public/cdk/preview` | `{code}`; проксирует preview и сохраняет привязку кода/токена сайта |
| `POST /api/v1/public/cdk/preflight` | Тело как у платформы; сохраняет Session для сайта |
| `POST /api/v1/public/cdk/redeem` | Публичная активация; сайт может добавить исключения карт/политику выбора |
| `GET /api/v1/public/cdk/result` | `?token=`; сохраняйте исходный `X-Redemption-Device` |
| `GET /api/v1/public/cdk/result-by-code` | `?code=` или `cdk_code`; восстановление по привязке сайта. Нет привязки — 404; IP/устройство всё ещё проверяются |
| `GET /api/v1/lookup/cdk` | `?code=` или `cdk_code`; локальная сводка в корне JSON, неизвестный код — 404 |
| `POST /api/v1/lookup/cdk/batch` | `{codes:[...]}` либо `{text:"коды по строкам"}`, до 100 уникальных; корневые `total/max/results` |
| `POST /api/v1/public/billing/check` | `{cdk_code}` либо `{token_input}` / `{session}`; корневые `summary/invoices/auth_source`, иногда `invoice_url` |

Поля сводки: `cdk_code/status/used/can_resubmit/message`, необязательные `account_email/plan/used_at/notes`. Типичные статусы: `unused/used/failed/disabled/expired/processing/unknown`. Это **локальная сводка, не доказательство списания**; одного `used=false` недостаточно для повторной оплаты. Проверяйте каждый элемент даже при HTTP 200. Решения о средствах принимайте по заказам и событиям платформы.

`result-by-code` сохраняет оболочку платформы, добавляя в корень `cdk_code/redemption_token/has_session_binding`, иногда ссылку на счёт. Проверяйте HTTP и исходный `code`: наличие токена не означает успех. Для счёта по коду нужен действительный Session, сохранённый на этом сайте; mailbox-активация и коды с других сайтов могут не иметь привязки. Нет привязки — 404, нет/неверные credentials — 400. Ответы могут содержать полный email и токены: передавайте их только уполномоченным держателям и не пишите в публичные журналы.

Пример (`CDK_SITE` — домен вашего сайта):

```bash
curl --get "$CDK_SITE/api/v1/public/cdk/result-by-code" \
  -H 'X-Redemption-Device: merchant-session-001' --data-urlencode 'code=<full CDK>'
curl "$CDK_SITE/api/v1/lookup/cdk/batch" -H 'Content-Type: application/json' \
  -d '{"codes":["<full CDK A>","<full CDK B>"]}'
curl "$CDK_SITE/api/v1/public/billing/check" -H 'Content-Type: application/json' \
  -d '{"cdk_code":"<full CDK>"}'
```

Прокси активации сохраняет `code/msg/data`; lookup и billing обычно возвращают корневой объект, ошибки сайта — `{error:...}`. Нельзя всегда читать только `data`. Для `/api/v1/admin/*` нужен JWT администратора сайта, не API-ключ платформы; конечным пользователям эти маршруты не предоставляются.

## 7. Вебхуки (события по картам, прямое пополнение и CDK)

### 7.1 Настройка URL вебхука

**Общий вебхук для mall:** сохраните HTTPS URL в «Разработчик → Общий вебхук», чтобы получать последующие терминальные события `gpt_direct.completed`, `gpt_direct.failed`, `gpt_direct.cancelled` с `source=mall`, `product` и стабильным `event_id`. Общий вебхук не отправляет прогресс/хронологию и не восполняет историю; для пропусков используйте §6.18.5b. Подписка отдельного ключа не получает заказы mall, не привязанные к нему. Заказы ключа с собственным настроенным вебхуком не дублируются в общий вебхук.

Настройки: `GET /api/v1/dev/webhook`, `POST /api/v1/dev/webhook`, тело POST — `{"webhook_url":"https://merchant.example/webhook"}`. Требуется JWT веб-сессии, не `X-API-Key`. Первое сохранение создаёт общий `webhook_secret`. Проверьте `X-Signature` как шестнадцатеричный HMAC-SHA256 исходного тела; обрабатывайте идемпотентно по `event_id`, возвращайте 2xx. В GPT-вебхуках `completed_at` остаётся Unix-секундами, а новый запрос использует RFC3339.

Для интеграции отдельного ключа настройте его вебхук на странице «Разработчик». События уровня ключа доставляются только подписанным ключам. Принимается только `https`.

### 7.2 Доставка

- Метод `POST`, тело `application/json`, UTF-8.
- Заголовок **`X-Signature`**: HMAC-SHA256 от **сырого тела запроса** (см. 7.7).
- Отвечайте `2xx` без задержек. Любой другой статус или таймаут считается неудачной доставкой.

### 7.3 Поля события

В каждом payload есть `event_id`, `type`, `created_at` и специфичное для типа тело.
Используйте `event_id` для дедупликации.

### 7.4 События по картам

Выпуск карты, пополнение, возврат, заморозка/разморозка, удаление и транзакции — с полями `card_id`,
маскированным `card_number`, `channel` (см. §6.11.1), суммами и статусом.

### 7.5 События жизненного цикла прямого пополнения и CDK

| `type` | Когда |
|---|---|
| `gpt_direct.progress` | Изменение статуса/стадии (до 30 на заказ) |
| `gpt_direct.completed` | Терминальный успех |
| `gpt_direct.failed` | `declined` или `failed_precharge` |
| `gpt_direct.cancelled` | Отменено |
| `gpt_direct.event` | В ленту добавлено событие |
| `cdk.reserved` / `consumed` / `released` / `frozen` / `unfrozen` / `disabled` | Жизненный цикл CDK |

Подписывайтесь на отдельные события либо используйте шаблоны `gpt_direct.*` / `cdk.*`.

> ★Имена событий сохраняют префикс `gpt_direct.` даже для заказов Claude и Grok.★ Читайте поле
> `product` в payload, а не имя события.

### 7.6 Соответствие событий и статусов

`gpt_direct.progress` может приходить много раз и **не** является терминальным сигналом.
Терминальны только `completed` / `failed` / `cancelled`. Прежде чем считать что-либо ошибкой,
прочитайте про автосмену карты в §6.18.5.

### 7.7 Проверка подписи (обязательно)

`X-Signature` = `HMAC-SHA256(webhook_secret, сырые байты тела запроса)`, **hex в нижнем регистре**.

- ★Считайте по **сырому телу**★. Не десериализуйте и не сериализуйте заново — байты будут отличаться,
  и проверка не пройдёт.
- Используйте сравнение с постоянным временем.
- Отклоняйте любой запрос с несовпадающей подписью.

### 7.8 Доставка, повторы и идемпотентность

- **Доставка не менее одного раза.** События по картам, сборам и балансу: до **3** попыток (задержки
  около `2s`, `4s`), затем доставка отбрасывается.
- События прямого пополнения и CDK (`gpt_direct.*`, `cdk.*`) доставляются через постоянную очередь:
  до **6** попыток с задержками около `10s`, `30s`, `2min`, `10min`, `30min`. Если адрес продолжает
  отвечать ошибкой, доставка на него приостанавливается и проверяется не чаще раза в 5 минут (пауза
  не расходует попытки); после восстановления события досылаются по порядку. Доставки, не принятые
  за 24 часа, отбрасываются. Адреса изолированы друг от друга, каждый получает свои события по одному
  и по порядку, поэтому недоступный адрес не задерживает вебхуки других получателей.
- Вебхук — это уведомление, а не источник истины. Если вебхук задерживается, проверьте заказ через API
  запросов, а не считайте его неудачным и не отправляйте повторно.
- Дедуплицируйте по `event_id` (например, `gpt_direct.completed:12345`,
  `gpt_direct.progress:12345:3`).
- Терминальные события прямого пополнения могут уйти на legacy-вебхук пользователя; события прогресса
  и CDK требуют вебхука, привязанного к API-ключу.

### 7.9 Рекомендации по безопасности

- Только `https`; проверяйте `X-Signature` **до** обработки.
- Никогда не логируйте полные номера карт, CVV и учётные данные.
- Относитесь к секрету вебхука как к паролю и меняйте его при утечке.

### 7.10 События баланса (`balance_change`) и сборов (`card_fee`)

#### `balance_change`

Отражает книгу операций аккаунта — **одно событие на строку книги**. Это авторитетный поток для учёта.

| Поле | Значение |
|---|---|
| `balance_log_id` | Id строки книги — **дедуплицируйте по нему** |
| `type` | Тип операции (`open_card`, `card_recharge`, `refund`, `transfer_in`, `transfer_out`, …) |
| `amount` | Со знаком: отрицательное — списание, положительное — зачисление |
| `before` / `after` | Баланс аккаунта до и после |
| `remark` | Человекочитаемое примечание (упрощённый китайский) |
| `ref_id`, `card_id`, `card_number` | Присутствуют, если строка связана с картой |

#### `card_fee`

Риск-сбор, начисленный по **конкретной авторизации**. Используйте для атрибуции, а не для учёта.

| Поле | Значение |
|---|---|
| `auth_id` | Id авторизации у апстрима — **дедуплицируйте по `auth_id` + `fee_type`** |
| `fee_type` | `decline` / `reversal` / `purchase_refund` / `micro_purchase` / `restricted_merchant` |
| `amount` | Начисленный сбор |
| `card_id`, `card_number` | Карта (маскированная) |

#### ★Не считайте дважды★

Один и тот же сбор приходит **и** в `balance_change`, **и** в `card_fee` (а сама покупка ещё и в
`card_transaction`). Это разные ракурсы одного события, а не три отдельных списания.

- Для **учёта и сверки**: используйте только `balance_change`. Он привязан к книге операций и полон
  без дублей.
- Для **бизнес-уведомлений и атрибуции**: используйте `card_fee` (содержит `auth_id`, поэтому
  сопоставляется с конкретной покупкой) и `card_transaction` (детали покупки).

Суммирование обоих потоков в баланс даст двойную или тройную сумму.

#### Семантика доставки

- **Не менее одного раза**: перезапуск между «доставлено» и «отмечено» приведёт к повторной доставке.
  Дедуплицируйте по `balance_log_id` (или по `auth_id` + `fee_type` для `card_fee`).
- Отправляются только **вновь возникшие** изменения баланса. Историческая книга не переотправляется
  при включении функции.
- Если URL вебхука не настроен, ничего не отправляется и ничего не накапливается — платформа всё равно
  помечает такие строки как обработанные.
- Правила подписи, повторов и таймаутов — как в 7.7 / 7.8.

## Приложение A: коды ошибок

**Всегда ветвитесь по `error_code`, а не по тексту `msg`** — `msg` предназначен для человека, меняется
между версиями и всегда на упрощённом китайском.

### A.1 Общие (любой эндпоинт)

| HTTP | `error_code` | Значение | Повтор |
|---|---|---|---|
| 401 | *(нет)* | API-ключ отсутствует / недействителен / отключён; аккаунт отсутствует или отключён | Нет — исправьте учётные данные |
| 403 | *(нет)* | Аккаунты службы поддержки не могут использовать Open API | Нет |
| 403 | *(нет)* | У ключа ещё нет списка разрешённых IP (для новых ключей он обязателен) | Нет — настройте |
| 403 | *(нет)* | Вызывающий IP не в списке разрешённых | Нет — добавьте IP |
| 403 | `RECHARGE_REQUIRED` | Нет зачисленного депозита; запись заблокирована (`data.recharge_required=true`) | Нет — внесите депозит |
| 403 | `FORBIDDEN` | Субаккаунт заморожен либо нет нужного права | Нет |
| 429 | *(нет)* | Превышен лимит (по умолчанию 100/мин на ключ) | Да — экспоненциальная задержка |
| 400 | `invalid_argument` | Неверный аргумент (некорректный id в пути, ошибка разбора JSON) | Нет |

| 400 | `insufficient_balance` | Недостаточно средств / резерва | Нет — внесите депозит |
| 400 | `request_failed` | Бизнес-ошибка; см. `msg` | Зависит |
| 400 | `forbidden` | Ограничено риском / не разрешено | Нет |
| 500 | `internal_error` | Ошибка сервера | Да — с тем же `Idempotency-Key` |
| 503 | `channel_unavailable` | Размыкатель канала открыт | Да, либо смените `issuer` |

**Идемпотентность**

| HTTP | Значение |
|---|---|
| 400 | Некорректный `Idempotency-Key` (допустимо: `A-Za-z0-9._:-`, 1–80 символов) |

| 400 | `insufficient_balance` | Недостаточно доступного баланса (при пакетном выпуске указывается «нужно $X, доступно $Y») |

| 403 | `API_SCOPE_UNAVAILABLE` | Область действия API-ключа недоступна |
| 404 | `ORDER_NOT_FOUND` | CDK-заказ не найден |

## Приложение B: чек-лист интеграции

Пройдите его перед запуском. Каждый пункт — реальная чужая ошибка:

- [ ] Ветвление по `error_code`; **нигде** в коде нет сравнения с текстом `msg`
- [ ] Все операции записи передают `Idempotency-Key`, а повторы используют **тот же** ключ
- [ ] HTTP **202** обрабатывается как «в процессе» и никогда не отправляется повторно — его возвращают возврат, удаление и создание заказа
- [ ] После `POST /gpt-direct/orders` вы **опрашиваете до терминального статуса**; 202 не считается успехом
- [ ] `product` — только `gpt` / `claude` / `grok`, **проверяется на вашей стороне**
- [ ] Для Claude / Grok значение `plan` берётся из `registry[].key` (без префикса), а не из ключа `plans`
- [ ] Заказы Claude / Grok явно передают `payment_country=US` и `payment_currency=USD`, цену читают из `registry[].checkout_amount_minor`
- [ ] Сборы, тарифы и доступность к покупке **читаются из `/gpt-direct/plans` во время работы**, а не захардкожены
- [ ] «Можно ли продавать» = тариф **есть в `registry`**, **и** `purchasable===true`, **и** `plans[acc_plan_key].enabled===true` — не читали несуществующее `purchased` и не смотрели только на `enabled`
- [ ] **Исходящий IP вашего сервера** внесён в список разрешённых для ключа (не IP браузера и не приватный адрес)
- [ ] Вы знаете, что у API-ключа есть **независимый накопительный лимит расходов**, отдельный от баланса аккаунта
- [ ] Вебхуки проверяют `X-Signature` по **сырым байтам тела** и дедуплицируют по `event_id` / `balance_log_id`
- [ ] Сверка использует только `balance_change`; `card_fee` / `card_transaction` не суммируются поверх
- [ ] Данные карты возвращают полный номер и CVV — в ваших логах они маскируются

### Действующие подписки: доплата за 5X/20X/50X

Метод возвращает доплату для конкретного аккаунта. Валюта берётся из счёта действующей подписки, а не из каталога новых подписок или выбранного региона.

1. Вызовите `POST /gpt-direct/preflight` и получите исходный `preflight_token`.
2. Вызовите `POST /gpt-direct/upgrade-quotes`, передав только `{ "preflight_token": "<исходный токен>" }`.
3. Выберите предложение с `available=true`. В `POST /gpt-direct/orders` передайте его новый `preflight_token`, соответствующий `plan`, полученную `currency` в поле `payment_currency` и обычные параметры карты/идемпотентности. Используйте `payment_mode=direct`.
4. Для выбранной карты вызовите `POST /gpt-direct/upgrade-funding-quote` с `card_id`, `plan` и токеном обновления. Формат ответа совпадает с обычной оценкой пополнения карты.

Проверка не создаёт заказ и не списывает деньги. Цена действительна не более пяти минут и привязана к пользователю, аккаунту, тарифу, сумме и валюте. Новый заказ требует действующего токена. После приёма заказа рост или снижение цены и истечение срока оценки не блокируют выполнение. Используется свежая доплата без сравнения со старой; временная недоступность предварительной цены не останавливает отправку, сумму определяет счёт провайдера. Перехода на полную стоимость или покупки промежуточного тарифа нет. Подписки из магазинов приложений, неактивные, с задолженностью и того же/более высокого уровня не поддерживаются. Обновление с нулевой доплатой автоматически не отправляется. Если свежего курса нет, цена показывается, но оплата недоступна. Сервисные сборы, выпуск и пополнение карты оплачиваются отдельно по действующим настройкам. `funding_usd_minor` — оценка средств на карте по свежему курсу с запасом 10%, а не сумма доплаты. Поддерживаются прямые платежи магазина и OpenAPI, но не активация CDK.

```json
{
  "quotes": [
    {
      "plan": "pro_5x",
      "current_plan": "plus",
      "available": true,
      "currency": "USD",
      "amount_minor": 8801,
      "minor_unit_exponent": 2,
      "funding_usd_minor": 9682,
      "expires_at": "2026-09-29T01:05:00Z",
      "preflight_token": "<opaque-upgrade-token>"
    },
    {
      "plan": "pro_20x",
      "available": false,
      "error_code": "upgrade_quote_unavailable"
    },
    {
      "plan": "pro_50x",
      "current_plan": "plus",
      "available": true,
      "currency": "USD",
      "amount_minor": 45000,
      "minor_unit_exponent": 2,
      "funding_usd_minor": 49500,
      "expires_at": "2026-09-30T01:05:00Z",
      "preflight_token": "<opaque-50x-upgrade-token>"
    }
  ]
}
```

Суммы в примере условные: `8801 / 10² = 88.01 USD`. Для JPY/KRW и других валют используйте возвращённый показатель, а не фиксированное деление на 100.


## Pro 50x: параметр тарифа и примеры запросов

Ключ тарифа 50x — **`pro_50x`**, поле запроса — `plan`. `promax` обозначает состояние подписки, а `chatgptpromax` — идентификатор провайдера; для создания заказа используйте `pro_50x`.

| Сценарий | Интерфейс / поле | Значение или правило |
| --- | --- | --- |
| Прямое пополнение | `POST /openapi/v1/gpt-direct/orders` | `"product":"gpt", "plan":"pro_50x"` |
| Выпуск CDK | `POST /openapi/v1/gpt-direct/cdks` | `"plan":"pro_50x"` |
| Доступные тарифы | `GET /openapi/v1/gpt-direct/plans?product=gpt` | В `registry` читайте `key="pro_50x"`, `purchasable` и `service_fee_usd_minor`; настройки находятся в `plans.pro_50x` |
| Повышение подписки | `POST /openapi/v1/gpt-direct/upgrade-quotes` | Выберите элемент `quotes[]` с `plan="pro_50x"` и `available=true`; передайте его новый `preflight_token` и указанную валюту оплаты |

Стандартный сбор 50x — **$0.15 за заказ**; для аккаунта с индивидуальным нулевым сбором возвращается 0. Используйте актуальный ответ `GET /gpt-direct/plans?product=gpt`. Оплата подписки, комиссии выпуска/пополнения карты и применимая доплата cs_live учитываются отдельно.

**Первое подключение 50x для бесплатного аккаунта:** выполните предварительную проверку в том же регионе, затем отправьте `POST /openapi/v1/gpt-direct/orders`. Замените `card_id` на доступную карту API-аккаунта, укажите собственные учётные данные и токен проверки.

```json
{
  "product": "gpt",
  "plan": "pro_50x",
  "card_id": 123,
  "credential": {
    "mode": "session",
    "session": "<YOUR_SESSION>"
  },
  "preflight_token": "<PREFLIGHT_TOKEN>",
  "payment_country": "PH",
  "payment_currency": "PHP",
  "client_request_id": "merchant-pro50x-20260930-001"
}
```

Передавайте заголовки `X-API-Key`, `Content-Type: application/json` и уникальный `Idempotency-Key`. При сетевом повторе сохраняйте ключ и `client_request_id`. HTTP 202 означает приём в очередь; продолжайте проверять тот же заказ.

**Выпуск CDK 50x:** `POST /openapi/v1/gpt-direct/cdks`. `funding_confirmed=true` подтверждает финансирование владельцем. При активации тариф берётся из CDK; параметр в запросе активации не превращает код другого тарифа в 50x.

```json
{
  "plan": "pro_50x",
  "count": 1,
  "funding_confirmed": true,
  "payment_country": "PH",
  "payment_currency": "PHP"
}
```

Для повышения Go/Plus/5x/20x используйте токен котировки `pro_50x` из `POST /openapi/v1/gpt-direct/upgrade-quotes`. Доплата определяется текущим счётом аккаунта, а не разностью цен каталога.


Цена PH без налога: PHP 29 008,93 (2 900 893 минимальных единиц), с налогом: PHP 32 490. Фактическая сумма определяется счётом. Отдельный настраиваемый лимит пополнения для50x — USD 1 000; лимиты прочих планов не меняются. Для CDK передавайте `plan: "pro_50x"`, суффикс бренда — `50X`. Процесс preview → preflight → redeem и выбор карты прежние.

## Подписки X Premium (первая версия)

Укажите `product=x` и plan: `basic_monthly`, `basic_yearly`, `premium_monthly`, `premium_yearly`, `premium_plus_monthly`, `premium_plus_yearly`. Новые подписки: US/USD, JP/JPY, PH/PHP, NG/NGN, TR/TRY, EG/EGP; по умолчанию JP/JPY. Регион проверки, заказа и CDK должен совпадать. Сумма JPY указывается в целых иенах, не в сотых долях.

С X-API-Key запросите `GET /openapi/v1/gpt-direct/plans?product=x`. Проверка и заказ: `POST /openapi/v1/gpt-direct/preflight` и `POST /openapi/v1/gpt-direct/orders`. Передайте product, plan, payment_country, payment_currency (например JP/JPY). credential.mode=session; credential.session — JSON-строка с auth_token, ct0, billing_email. Для заказа также нужны принадлежащий вам card_id, preflight_token, client_request_id и credential.

Для X CDK используются те же короткие ключи plan и данные X. Внешние карты, повышение действующей подписки и автоматическая отмена автопродления пока не поддерживаются. Управляйте продлением в настройках X. Функцию и тарифы должен включить администратор; документация не означает доступность в рабочей среде.
